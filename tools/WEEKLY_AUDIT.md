# Базовый аудит доказательств (К7a)

`weekly_audit.py` — первый локальный read-only срез #74/#163. Он читает
существующие `registry.sqlite` и `project-governance/documents.json`, но не
создаёт собственную базу, не открывает зарегистрированные документы, не
запускает модели и не обращается к провайдерам. В отчёте только суммы, даты
порогов и состояние источников; пути, имена узлов и содержимое не выдаются.

```sh
python3 tools/weekly_audit.py \
  --registry /путь/к/LLM/registry/registry.sqlite \
  --documents /путь/к/LLM/project-governance/documents.json \
  --as-of 2026-09-24 --max-age-days 30
```

`observed` означает только успешное чтение метаданных. `unavailable` с причиной
означает неизвестное значение, а не ноль; CLI завершится с кодом 2. Старой
считается дата `verified_at` строго раньше указанного порога. Отсутствующая
или некорректная дата считается отдельно. `missing_required` — количество
строк, где отсутствует хотя бы одно поле, требуемое для паспортной карточки;
одна строка может входить и в счётчик старой проверки. Для документов
`inventory_or_unreviewed` — известные статусы каталога, не доказательство
ошибки содержимого. Отсутствующий SHA считается отдельно, но совпадение SHA с
файлом этим срезом не проверяется.

Проверка: `python3 -m pytest -q tools/test_weekly_audit.py`; отдельный CI
`weekly-audit.yml` выполняет этот тест и Ruff. Скрипт не
подключён к расписанию и пока не интегрирован в окно. Противоречия знаний,
повторные ошибки, использование навыков, успешность бэкапа, использование
памяти в ответах и покрытие чатов выжимками явно перечислены в
`not_measured`: для них нужны подтверждённые источники К4/К6 и отдельные
проверки. До этого экран не должен показывать их как ноль или «зелёные».

Готового инструмента, который знает схему владельческого реестра и каталога,
нет; использован стандартный модуль SQLite/JSON Python без новой зависимости.
